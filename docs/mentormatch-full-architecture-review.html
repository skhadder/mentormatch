A Executive Summary

MentorMatch is a well-structured, intentionally minimal Next.js 16 App Router monolith built as a hackathon prototype. Its stated purpose — transparent, fairness-tested mentor matching for students without professional networks — is served effectively by the current architecture. The codebase is noticeably thoughtful for a prototype: domain logic is cleanly separated from HTTP concerns, AI is optional at every call site, and a fairness audit is structurally enforced and tested.

However, the architecture has a small number of serious correctness issues that would cause real data integrity problems under load, three security gaps that are trivially exploitable, and several reliability and maintainability issues that would compound as the application grows. None of these require architectural rewrites — they are all fixable with targeted, low-risk changes to existing files.

The three most impactful improvements, in order:

  1. Fix the write-concurrency race condition in lib/store.ts — it allows mentor over-booking and corrupted capacity counts.
  2. Add a secret-header guard to the three unauthenticated write surfaces — the mentor PATCH/DELETE routes and the seed reset route expose the entire data store to anonymous mutation.
  3. Add per-IP rate limiting to the AI routes — one HTTP loop can exhaust the Anthropic quota and incur unbounded cost.

The current architecture is appropriate for a demo/prototype. It is not yet appropriate for a public deployment with real mentors and real students. The changes required to reach production-readiness are moderate in scope and do not require a platform change.

Layer Structure

The application follows a clean 3-layer architecture:

  • Domain layer (lib/) — pure or near-pure TypeScript functions with no framework dependencies. Covers: types, matching algorithm, request lifecycle rules, fairness audit, playbook generation, mentor settings validation, input parsing, and AI client wrapper.
  • API layer (app/api/) — thin Next.js route handlers. Each file is typically 10–25 lines. Responsibilities: parse input, delegate to domain functions, return JSON. No business logic lives here.
  • UI layer (app/ pages + components/) — React 19 client components. State is managed locally in each page. No global state manager (no Redux, Zustand, Context). Cross-page state passes through sessionStorage and localStorage.

Data Flow — Student Path

1. Intake (/find) — Student fills in 6 questions. Answers are saved to sessionStorage via lib/client.ts:saveProfile(). No server call until submit.
2. Match (/results) — On mount, the saved profile is POSTed to /api/match. The server runs matchMentors() + attaches template explanations. Results render immediately. Then, up to 3 parallel POSTs to /api/explain upgrade each explanation with AI; the UI shows skeletons while these resolve.
3. Playbook (/playbook) — On mount, the mentor ID is read from sessionStorage, the public mentor profile is fetched, the template playbook renders immediately, then /api/playbook is called to upgrade with AI output.
4. Request (/playbook → dialog) — Student writes a message in a modal, POSTs to /api/requests. The request ID is saved to localStorage. Student can later visit /requests to check status.

Data Flow — Mentor Path

1. Portal (/mentor) — Student selects a demo mentor (no real auth). ID saved to sessionStorage.
2. View portal (MentorPortal) — GET /api/mentor/[id] returns the mentor object + all their requests. Mentor can PATCH settings or DELETE (opt-out) their profile. Requests can be accepted, declined, or merged.
3. All mutations go through lib/store.ts:mutate(): load JSON → run domain function → save JSON.

E Detailed Recommendations

Critical — F-01 Fix the write-concurrency race in lib/store.ts

What: mutate(fn) loads the DB, runs the mutation, and saves — but nothing prevents two simultaneous HTTP requests from both loading before either saves.
Where: lib/store.ts:mutate(), called by every state-changing route handler.
Why it's a problem: Next.js handles concurrent requests in the same process. Two students hitting "Send request" simultaneously can both see the same available capacity, both increment requests_this_month, and both save — leaving the mentor double-booked.
Fix: Wrap all calls to mutate() with an async mutex. The async-mutex npm package is zero-dependency and battle-tested. 

// lib/store.ts
import { Mutex } from "async-mutex";

const _lock = new Mutex();

export function mutate<T>(fn: (db: Db) => T): Promise<T> {
  return _lock.runExclusive(() => {
    const db = loadDb();
    const out = fn(db);
    saveDb(db);
    return out;
  });
}

Effort: Low — one file, one new dependency, change signature from sync to async (callers already use await mutate(...) or are route handlers that can be made async).

High — F-02 Guard mentor write routes with a shared secret header

What: PATCH, DELETE, and POST actions on /api/mentor/[id]/* require no proof of identity. Any client can modify any mentor.
Why: For a demo, full OAuth is overkill. A shared secret stored in the browser session at "claim" time gives meaningful protection with minimal complexity.
Fix: When a user "claims" a mentor in app/mentor/page.tsx, generate a random token, store it in sessionStorage, and send it as an X-Demo-Token header. The server stores the token alongside the mentor ID in the DB and validates it on write routes. 

// lib/client.ts — on "claim"
export function claimMentor(id: string) {
  const token = crypto.randomUUID();
  sessionStorage.setItem("mm_mentor", id);
  sessionStorage.setItem("mm_token", token);
  return token;
}

// api() should inject the token automatically:
const token = sessionStorage.getItem("mm_token");
const headers = { "Content-Type": "application/json" };
if (token) headers["X-Demo-Token"] = token;

// lib/api.ts — server-side guard helper
export function requireToken(req: Request, expectedToken: string | null): boolean {
  return req.headers.get("X-Demo-Token") === expectedToken;
}

Effort: Medium — requires storing token in DB on claim, and reading it in each write-route handler.

High — F-03 Protect /api/seed from anonymous use

What: One HTTP POST with no body wipes the entire database.
Fix (Option A — simplest): Gate behind an environment variable secret. 

// app/api/seed/route.ts
export async function POST(req: Request) {
  const secret = process.env.SEED_SECRET;
  if (!secret || req.headers.get("x-seed-secret") !== secret)
    return fail("Forbidden.", 403);
  return guard(() => { resetDb(); return ok({ reset: true }); });
}

Fix (Option B — safer): Disable the route entirely in production via an env check: if (process.env.NODE_ENV === "production") return fail("Not available.", 404);

Effort: Low — 3-line change.

High — F-04 Add rate limiting to AI routes

What: /api/explain and /api/playbook make live Anthropic calls with no per-IP throttle.
Fix: A simple in-process token-bucket keyed by client IP is sufficient for a single-process demo. For a deployed app, use Next.js middleware or a Vercel rate-limit edge function. 

// lib/rateLimit.ts — simple in-process bucket
const buckets = new Map<string, { count: number; resetAt: number }>();
const WINDOW_MS = 60_000;
const MAX_CALLS = 5;

export function checkRateLimit(ip: string): boolean {
  const now = Date.now();
  const b = buckets.get(ip);
  if (!b || now > b.resetAt) {
    buckets.set(ip, { count: 1, resetAt: now + WINDOW_MS });
    return true;
  }
  if (b.count >= MAX_CALLS) return false;
  b.count++;
  return true;
}

// In /api/explain/route.ts and /api/playbook/route.ts:
const ip = req.headers.get("x-forwarded-for") ?? "unknown";
if (!checkRateLimit(ip)) return fail("Too many requests.", 429);

Effort: Low — one new helper file, two route changes.

Medium — F-06 Auto-reset requests_this_month at month boundaries

What: The capacity counter never resets, causing mentors to become permanently full.
Fix: Store a month_key string on each mentor (e.g., "2025-07"). On loadDb(), compare against the current month; if different, reset the counter and update the key. 

// In lib/types.ts — add to Mentor:
month_key?: string; // "YYYY-MM"; absent = needs reset

// In lib/store.ts:
export function loadDb(): Db {
  const db = /* ...existing load logic... */;
  const thisMonth = new Date().toISOString().slice(0, 7);
  for (const m of db.mentors) {
    if (m.month_key !== thisMonth) {
      m.requests_this_month = 0;
      m.month_key = thisMonth;
    }
  }
  saveDb(db); // persist the reset
  return db;
}

Effort: Low — 10 lines, one type change (optional field, backward-compatible).

Medium — F-08 Strengthen AI output validation in /api/explain

Medium — F-09 Add a module-level in-memory cache to lib/store.ts

What: Every request re-reads the entire JSON file from disk, blocking the event loop.
Fix: Keep the parsed Db in a module-level variable; invalidate it on every write. 

// lib/store.ts
let _cache: Db | null = null;

export function loadDb(): Db {
  if (_cache) return _cache;
  try {
    _cache = JSON.parse(fs.readFileSync(file(), "utf8")) as Db;
  } catch {
    _cache = freshDb();
    saveDb(_cache);
  }
  return _cache;
}

export function saveDb(db: Db) {
  _cache = db;          // update cache before disk write
  fs.mkdirSync(path.dirname(file()), { recursive: true });
  const tmp = `${file()}.tmp`;
  fs.writeFileSync(tmp, JSON.stringify(db, null, 2));
  fs.renameSync(tmp, file());
}

export function resetDb() { _cache = null; saveDb(freshDb()); }

Effort: Low — 8-line change in one file. Note: this cache is process-local; in a multi-process deployment (PM2 cluster, multiple Vercel instances) the cache would be stale. For single-process demo use this is correct and safe.

F Alternative Architecture Analysis

Three plausible architectural alternatives are evaluated below. All are assessed against the application's actual scope and the identified weaknesses.

Option 1 — Replace the JSON file store with SQLite (via better-sqlite3)

What it looks like: Replace lib/store.ts with a SQLite database. Two tables: mentors and requests. All current domain logic in lib/requests.ts and lib/matching.ts remains unchanged — only the persistence layer changes.

Problems it solves:

  • F-01 (race condition) — SQLite's write serialisation guarantees atomic transactions without a mutex.
  • F-09 (full DB re-read) — Queries load only what is needed; no full-file parse.
  • F-10 (O(n) scans) — Indexed lookups for WHERE id = ? and WHERE mentor_id = ?.
  • F-06 (month reset) — A column default and a simple UPDATE query.
  • F-05 (no schema validation) — SQL schema enforces types and constraints.

Advantages: Solves 5 confirmed weaknesses at once; better-sqlite3 is synchronous and zero-config (one file, no server); the domain layer is completely unaffected.

Disadvantages: Migration effort (~1–2 days); better-sqlite3 requires a native build (node-gyp); not compatible with serverless/edge runtimes without @libsql/client or similar. The current JSON approach works fine for a single-server demo.

Verdict: Recommended if the application moves toward production. Not necessary for the current prototype — the mutex fix (F-01) and in-memory cache (F-09) are cheaper and lower-risk short-term improvements that achieve the same safety within the demo's single-process constraint.

Option 2 — Add a proper authentication layer (e.g., NextAuth.js)

What it looks like: Replace the "View as mentor" selector with real sign-in. NextAuth.js supports GitHub/Google OAuth in ~50 lines of configuration. Session tokens replace the sessionStorage-based demo approach. Mentor write routes check session.user.id against mentor.owner_user.

Problems it solves:

  • F-02 (no auth on write routes) — Fully solved.
  • F-03 (unprotected seed) — Seed can be gated to admin users.

Advantages: Production-grade; enables real mentor onboarding.

Disadvantages: Requires real user accounts, a callback URL, an OAuth app registration, and database changes to store user-mentor relationships. This is a significant scope increase for what is explicitly a hackathon prototype with 50 fictional mentors.

Verdict: Not justified for the current prototype. The shared-secret header approach (Recommendation F-02) provides adequate protection at a fraction of the implementation cost. OAuth should be the first step when real mentors are onboarded.

Option 3 — Microservices / separate matching service

What it looks like: Separate the matching engine into its own Node.js service or serverless function, with the Next.js app calling it over HTTP/gRPC.

Problems it solves: Theoretical independent scaling of the matching computation.

Advantages: Matching could be deployed independently; different teams could own different services.

Disadvantages: The matching algorithm is pure synchronous TypeScript that runs in under 1ms for 50 mentors. A network hop would add 10–50ms with zero computational benefit. This would introduce distributed-system complexity (network partitions, service discovery, contract testing) for a function that currently has zero operational cost.

Verdict: Not recommended at any scale this application is likely to reach. The current monolith is the correct architecture. The matching engine's clean separation into lib/matching.ts already provides the logical isolation that microservices would seek to enforce at a network boundary.

H Overall Assessment

Architectural Strengths

Excellent domain/infrastructure separation. Every piece of business logic lives in lib/ as pure or near-pure functions. Route handlers are thin, testable adapters. This is the single most valuable architectural decision in the codebase — it makes the matching algorithm independently testable and the fairness audit structurally enforceable.
AI is never on the critical path. Every AI call site has a complete, immediately-rendered template fallback. The application delivers its full value proposition with the API key removed. This is a correct and mature design for an AI-enhanced application.
Fairness is architecturally enforced, not just documented. The proxy-based test in matching.test.ts proves the matcher cannot read display_name or name, even if a bug accidentally introduces such a read. This is a sophisticated and reusable testing pattern.
Input validation is centralised and exhaustive. lib/profile.ts and lib/mentorSettings.ts handle all validation. No route handler re-implements validation logic. The allowlist pattern in EDITABLE prevents accidental mass-assignment vulnerabilities.
Atomic file writes prevent partial-write corruption. The tmp-file rename in saveDb() is the correct OS-level primitive for this. It prevents a crash mid-write from leaving a half-written JSON file.
No unnecessary dependencies. The entire application runs on 4 runtime dependencies (Next.js, React, React-DOM, Anthropic SDK). The icon system is self-contained SVG. No icon library, no state manager, no form library.

Biggest Weaknesses (confirmed)

  1. The write-concurrency race condition (F-01) is the most serious confirmed correctness bug. Under any realistic concurrent load it will produce incorrect capacity counts and allow mentor over-booking.
  2. Unauthenticated write surfaces (F-02, F-03) make the entire data store modifiable by any anonymous HTTP client. This is an accepted trade-off for a prototype but must be addressed before any real use.
  3. No rate limiting on AI routes (F-04) creates an unbounded cost exposure. A single automated script could exhaust the API quota in minutes.

Top Three Improvements to Implement First

  1. Async mutex in lib/store.ts — one file change, one small dependency, fixes the most serious correctness issue.
  2. Secret-header guard on /api/seed — 3 lines, removes the trivial data-destruction vector.
  3. In-process rate limiter on AI routes — one new helper file, two route changes, removes unbounded cost exposure.

Is the Current Architecture Sufficient?

For a hackathon prototype with 50 fictional mentors: yes. The layered structure, clean domain separation, and fairness audit are all above the standard for a prototype. The codebase is well-organized and readable.

For a public deployment with real mentors and real students: not yet. The four Priority 1 fixes are non-negotiable before exposure to real users. The Priority 2 fixes (month reset, cache, structured logging, extended tests) are necessary for operational stability. The architecture itself does not need to change — only the gaps in its guards and observability need to be filled.

If the mentor pool grows beyond ~500 mentors or requests beyond ~5,000: replace the JSON file store with SQLite. This single change resolves the concurrency, caching, scan-complexity, and schema-validation findings simultaneously, while leaving all domain logic untouched.
